# 开发者业务行为图

目标是让开发者回答：哪段核心代码在做什么，什么输入/关系让它选择这条路径，等待依赖什么，真实效果是否提交。Skill 在开发对话中伴随工作；探针和观测服务负责程序运行期间的持续采集。

本 Skill 是贯穿开发前、中、后的一条必需支线，负责业务约定、状态机、源码关联、探针和一致性检查。用户可以采用任何设计方法、框架、开发流程或编码 Skill；本 Skill 不接管这些选择。开发主线每次改变相关行为时，同步维护这条支线的产物，再用检查连接前后的约定与真实执行。新项目和重要行为修改先读 [全过程开发与白盒契约](references/continuous-development.md)。先建立独立预期、参数/函数约定和测试接口，再逐步实现；未接入的检查保持待验证。

## 用户只需讨论需求和查看图

开始时，通过几轮简短对话提炼业务、状态和规则，展示当前关注的局部图，让用户纠正含义。用户决定的是软件怎样工作，不是观测文件或检查命令怎样组织。

进入开发后，AI 自行完成下述记录、解析、映射、埋点、生成、审阅与检查，不要求用户逐步运行命令、填写 review.json 或批准常规同步。进度只说明与功能有关的发现；命令、指纹、文件清单和中间日志保存在项目内部，除非用户要调试接入过程，否则不逐项展示。遇到能自行修复的技术问题先修复；只有新的业务歧义或冲突才回到具体问题。

每轮完成时，给出可打开的更新图、简短变化说明、相关运行结果及确有的缺口。用户可在图中展开、搜索、查看参数和源码，继续提出修改。保留其位置、名称、备注和关注范围。不要把“先让用户维护观测材料”变成使用前提。

这些步骤由使用本 Skill 的 AI 执行，安装文件本身不会后台监听所有编辑器。首次接入时保留已有约定，在项目的 AI 指令文件（如 AGENTS.md）中补充后续修改须遵守的范围、Skill 位置及检查入口，并把同步检查接入项目已有验证脚本或 CI。没有 AI 指令文件时可建立项目内文件，不安装全局 hooks。按 [后续会话约定](references/continuous-development.md#后续会话约定) 写入本项目的实际命令；未接入自动触发时如实说明，不能声称所有外部修改都会自动同步。

## 每次编码都维护模型

新增功能、修复和重构都以一个可验证的小变更为单位。修改前记录本次请求、允许改变的需求及旧基线；编码过程中一起维护程序、业务分组、局部结构、状态机、探针和反例，不等程序写完后再总结成图。行为未变时允许保留上层抽象，但须说明依据，不能为“同步”机械改动每层。

Python 项目按 [伴随修改与检查机制](references/cochange.md) 接入 `code_structure.py` 和 `change_sync.py`。确定性静态分析生成局部函数/参数/条件/调用候选；业务理解选择关注范围、分组、约束和可观察量；实际运行提供状态、判定和提交事实。三者分别保留来源，不能互相代替。新增入口、动态调用和未映射符号明确分类，不能因没有进图就视为无业务影响。

接入检查后，每个变更遵循 `begin → 编码/投影/inspect → verify → accept → check`。`verify` 比较实际加载的状态机、必需探针及独立业务预期，绑定本次源码、模型、需求、检查脚本和工具版本。检查失败不得报告“已同步”；先定位漏改、实现偏离或需求待明确之处。不能改写既有预期迎合实现，也不能仅重新 capture 消除报错。用户确实改变需求时，使用本次已记录的需求范围更新相应预期，其他保护保留。

检查命令应进入项目已有测试或 CI 的交付入口；未接入或未运行时，直说只有工作流程约束。Skill 提示本身不能强制所有编辑器和 AI 遵守，也不能证明未建模行为或任意自然语言说明正确。不擅自安装全局 hooks。

新项目在 `sync.json` 配置 `whitebox`，用 `whitebox_contract.py` 检查关键函数、参数类型、真实输入/输出和条件结果。开发前用 plan 检查约定，编码中 inspect 核对源码，verify 核对真实事件；不要只核对最终 HTTP 或页面结果。采用 [验证规则](references/validation-rules.md) 构造适用的正反例、序列、并发与定向改错检查。

## 澄清和建模

首次接入和行为需求变化时，先按 [需求提炼与反问](references/requirements-dialogue.md) 形成顶层业务链或业务网：参与者、业务对象、开始事件、关键动作、分支/并发/依赖和实际成功效果。用简短的业务表述向用户说明当前理解；将推断与已确认规则分开。不要直接从笼统需求跳到函数实现，也不要让用户从空白替你设计整张图。

主动找出会改变状态转换、权限、参数版本、资源占用、取消和恢复行为的关键分歧，按影响和依赖分轮询问，通常每轮 1–3 问。问题带具体场景、可选行为及其后果；不照搬整套问卷，不重复已有答案，不为普通可逆实现选择打断用户。已经问出的问题保持等待，沉默和默认选项不算回答；不依赖答案的工作继续推进。用户明确授权自行选择时，记录选择及授权范围。“实现细节由你决定”不能自动关闭未定的业务选择，例如取消单次运行还是整个任务；只有可从已确认规则直接推导，或用户确实将该业务选择交给你决定，才不用再问。

答案必须更新顶层节点/边、状态条件、核心参数/函数映射和测试。部分回答仅关闭对应问题；明确修订保留旧答案和变更依据；矛盾的要求先澄清。项目内用 `discovery.json` 记录来源、业务网、问题和决定，新接入项目在 sync.json 配置 discovery。`requirements_dialogue.py questions` 整理本轮未问问题，`check` 及已接入的 change_sync 拒绝未解决的关键分歧和缺失的需求/图/测试映射。脚本检查记录，不能替代发现遗漏问题的语义判断。

先判断软件适合哪些行为视角：流程/状态机、并发活动、数据流、事件协议、数据约束或连续控制。有并发、等待、汇合和共享容量时，把这些语义融入项目已有机器和节点关系：活动何时可执行、占用多少资源、等待什么、何时归还、哪些活动都完成后才能继续。按 [完整内部状态与原图表达](references/integrated-execution.md) 接入；不因借鉴 Petri 就默认另造一套权威状态或单独的分析页面。项目已经使用 Petri 引擎时，可保留它作为内部执行机制，原图仍通过同一活动身份展示状态。其他模型取舍见 [多模型与工作网](references/worknets.md)。

先读用户最新意图、项目约定和已有模型，保留已确认决定，不把示例领域变成通用规定。当前要实现的行为已经明确时结束提问，直接推进已授权的开发；无需再让用户批准整份需求文档。

选一条业务流，连接动作/状态 → 核心函数 → 关键输入输出 → 条件与关系读取 → 等待/恢复 → 实际效果。明确需要保留的业务可观察量和反例。新增代码时先形成候选模型与探针位置再实现；已有项目从入口、关键计算、权限读取、判定和提交点抽取候选，不能为了图简约删掉决定行为的函数或参数。

读 [开发流程](references/developer-workflow.md)。模型使用 [行为模型契约](references/behavior-model.md)。借鉴静态代码图、知识图谱或状态机时，保留它们的证据类型：语法/调用结构、人工或 LLM 语义声明、实际运行事实、独立符合性检查分开。

## 程序自身的状态机

在开发生命周期逻辑时，定义状态枚举、嵌套关系、事件载荷、上下文类型/范围、guards、动作及恢复语义，并集成到程序的实际执行。按语言和项目已有机制选用成熟状态机；同一声明用于执行与导出图，避免观察器事后模拟另一套状态。阅读 [运行状态机](references/runtime-statechart.md)，按事务边界验证迁移和实际效果。状态机负责业务执行，探针负责采集，两者职责不同。

“处理中”可以是上层摘要，但底层须保留范围内每项执行活动的状态和实例身份。完整配置包含主流程、并行活动、资源与等待条件；折叠只是视图操作。新运行不能覆盖仍在结束的旧运行。查询应能列出全部活动实例，并按运行、参数版本和活动定位；未覆盖的普通函数局部变量或外部系统明确列出，不能假称已全量监控。主流程的推进条件必须检查同次运行的内部完成事实。

## 伴随编码插钉子

先按 [源码归属与隔离](references/source-isolation.md) 约定业务层、中立接口、观测适配器和生成目录。应用状态机/工作网属于业务，观测实现可移除；业务层不得反向导入 skill 运行库。适配文件可用 `bo_`、适配类用 `BO` 前缀，业务变量保留领域名称。生成输出必须可追溯到生成器/模板，开发者编辑源，重生成后再验收。

读 [语义探针](references/semantic-pins.md)，按项目适配 `scripts/semantic_probe.py`。显式选字段，分别记录关键函数入/出、权威读取、条件实际判断、等待/恢复和提交后效果。传递 attempt/entity/build/call 身份；依赖引用具体事件与关系类型，调用先后只进入时间线，不能自动成为因果边。

不要把探针当业务判定源。结果由原程序决定；在故障隔离内构造探针载荷，热路径不等待磁盘或网络。关闭、抛错、队列满与丢事件时都要核对业务结果和真实效果。采集缺口显示 unknown/gap，不能补造路线。

## 绑定和同步

Python 参考工具只读解析 AST、核对符号和文件内容；`code_structure.scan` 按内容复用未改文件，`enrich` 保留业务节点并生成局部调用节点和边。其他语言需对应解析/符号工具及同样的变更契约，不能套用 Python 检查结果；AST 不是完整数据流分析。

```text
python <skill>/scripts/behavior_model.py validate --root <project> --model behavior.json
python <skill>/scripts/behavior_model.py capture --root <project> --model behavior.json --out manifest.json
python <skill>/scripts/behavior_model.py check --root <project> --model behavior.json --baseline manifest.json
python <skill>/scripts/behavior_model.py events --root <project> --model behavior.json --events events.jsonl
```

以上为底层工具和旧项目兼容命令。启用变更检查的项目，由 `change_sync accept` 在校验通过后更新 manifest。源码修改前先核查旧基线，过程保留影响节点与失败证据。启动须在业务模块加载前绑定并核对；磁盘新源码不等于正在执行的代码。开发中的候选图与旧进程的运行事实分开，新构建验证并加载后才接入新事实。capture 只证明内容对应，不证明图或权限语义正确。

## 开发者调试页

在需求讨论和迭代中，按 [局部图与共享](references/focus-and-sharing.md) 用 `focus_graph.py` 从同一完整图输出当前关注部分及边界，供用户确认；不要另画没有原始身份对应的业务图。运行事实只在指定运行与构建下叠加。导出审查或复现材料使用 `project_bundle.py` 的显式清单与完整性检查。

使用一张可拖拽的节点连接图。业务步骤、函数、状态、参数、判断和资源是不同类型的节点，通过包含、调用、传值、判断依赖和状态迁移连接；不把“业务与代码”和“流程状态”做成互斥页面。用形状、颜色与简短标签区分类型，避免把每个节点做成大段文本卡片。关键类型/值、结果和等待条件直接出现在图上，详细值与源码可在节点旁打开。

以业务链路控制展开范围：展开时保留原节点与邻近关系，内部函数、条件和参数加入同一画布。提供算法布局、节点拖拽和固定位置；保存手动坐标、展开状态与视野。运行刷新不得重排节点，新增节点优先局部放置；用户明确执行自动布局时调整未固定节点，并提供撤销。阅读 [分层图与渲染](references/hierarchical-graph.md)。`assets/stategraph-viewer/` 提供 PixiJS/WebGL 与 ELK 参考实现；旧 `assets/developer-viewer/` 仅供兼容。

当前快照、选中尝试、历史事件分别标明。静态关系与实际走过的边可辨；未知、过期、失败、运行中和已提交分开。多候选审批展示每条求值及最终 any/all 结果，不只展示最后一条；恢复显示当前缺失条件和触发方式。页面保持简明，把研究报告、能力说明、测试计数放文档。

允许开发者修改各类节点的显示名称并添加备注。名称、备注、当前关注节点和逐层展开状态按稳定项目/节点 ID 保存；重新生成图不能覆盖个人标注。保留原始名称与源码身份，修改显示文字不等于重命名源码或更改规则。刷新、折叠再展开及切换运行时验证保存与恢复；存储失败明确提示。

搜索覆盖完整图中的名称、函数、参数和备注，包括收起的内部节点。选择结果时只展开其所属层级并定位到该节点，保留其他区域的展开状态和已保存位置；搜索结果不改变规则或运行事实。

涉及 ReBAC 时，先用 [权限情况清单](references/authorization-patterns.md) 识别适用的直接授权、群组、角色、继承、组合、排除、租户和上下文情况，再按 [规则与判定依赖图](references/rebac-graph.md) 接入。示例的一跳规则不是通用限制；已声明的递归继承必须正确表达。同图展开规则组合、关系事实、参数及实际子检查，区分规则定义、一次求值结果、执行状态与结果是否仍适用；未求值、缺失、过期和拒绝不能混为一类。先确认引擎和真实证据范围，不能从普通布尔响应补造解释路径。布局与样式资源使用明确的开源许可证，保留第三方声明。

界面和场景文案用具体操作与因果句，例如“等待可用名额”“两项检查都通过后才能提交”。函数名、参数类型、实际值保留在相应节点；采集协议词、工具内部缩写和实现编号不作为主要业务说明。场景分别写清操作条件和预期结果，不能用一个模糊英文代号代替。信息是否充分以开发者能解释当前运行和定位源码为准。

## 验证与交付

除变更门禁，接入 `architecture_guard.py check` 检查文件归属、导入方向和生成内容；可用 `package` 导出独立业务核心，并实际执行导出的包。只有通过 core 包运行才能声称本项目已验证观测层可剔除。对工作网使用 `worknet_contract.py` 比较运行声明、重放实际变迁、检查资源守恒；同步配置的 `required_worknet_cases` 指定哪些用例必须提供真实标记。需求新增、函数重构和 bug 修复分别保存有源码版本的图快照，不能覆盖旧图后声称已验证迭代变化。

采用内嵌活动配置时，`execution_contract.py` 检查原节点身份、资源/汇合边、主状态推进条件及真实内部更新；`required_execution_cases` 指定必须返回完整配置的场景。至少覆盖资源不足时等待、资源足够时实际重叠、未完成不能推进、旧新运行同时可查，以及回看时不借用未来结果。已有工作网协议仍供旧项目兼容，不能用它取代新项目的融合设计。

除了业务反例，还亲自完成开发者任务：从图找源码；读参数/返回值解释分支；找等待和恢复条件；定位一次刻意问题或需求变更；核对磁盘、加载版本、图和事实。用真实运行和浏览器操作留证，直接读取权威效果。schema、指纹、单元测试不能代替这些任务。

必要时按已有授权做独立 Skill 使用测试，只提供真实需求、Skill 和原始材料，不透露预期答案。区分开发者任务场景、独立 agent 和真人试用；没有真人数据不声称已证明易用性。

交付简短调用示例、可打开的观测地址、源码和复现命令、实际覆盖与未知范围。后续图控制可预留 command 契约，但图编辑不会产生授权；执行必须走程序原有命令、鉴权和提交保护。

## 兼容旧项目

`model_tool.py`、`probe.py`、`viewer_server.py` 和旧 `assets/viewer`/schema 保留 v1 项目复现。新开发采用本页伴随修改流程；旧 `references/model.md`、`workflow.md`、`instrumentation.md` 的终端用户视图原则不适用于开发者界面，不用它们覆盖本页。
