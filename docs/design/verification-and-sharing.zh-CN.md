## 开发前要构建哪些测试材料

| 产物 | 必须包含 | 由谁维护 |
|---|---|---|
| 场景说明 | 初始条件、具体操作、预期结果、对应需求、来源与未决项 | 本 Skill 与用户澄清后形成 |
| 合成数据 | 对象、关系、参数、资源配置、受控时间、数据版本及重置方式 | 本 Skill 准备，编码阶段接入适配器 |
| 独立预期 | 许可/拒绝、状态变化、等待与恢复、效果对象/数量、应保持的约束 | 基于已确认需求；不由被测实现回填 |
| 模型执行材料 | 状态/规则声明、模拟输入、可执行检查、模拟范围 | 本 Skill 建立，复用应用声明或成熟引擎 |
| 运行适配契约 | 如何启动真实程序、发出操作、等待结束、读权威结果和清理合成数据 | 本 Skill 定义；编码 Skill 实现 |
| 探针计划 | 位置、必要字段、触发场景、关联 ID、预期缺口处理 | 本 Skill 定义；编码 Skill 绑定源码 |
| 序列与定向改错方案 | 操作生成范围、必须成立的性质、要刻意破坏的规则与预期失败检查 | 本 Skill 按业务风险选择 |
| 结果格式 | 用例/需求 ID、实际构建、数据依据、预期与实测、失败节点、证据位置 | 检查程序产生 |

机器可读的场景建议包含：

```text
case_id, requirement_ids, rule_ids, source_refs,
initial_fixture, operations,
expected_decisions, expected_states, expected_effects, invariants,
observation_requirements, isolation_and_reset, decision_status
```

这些字段是设计清单，实际格式沿用项目测试体系。场景说明可以由同一份结构化场景生成 Markdown，避免维护两份预期。

开发前可以演示模型运行，并展示最关键的正例和反例。若用户纠正预期，将其作为需求变更保存。检查关键语义，不强制用户确认每个技术测试。

“可交给编码”与“实现已验收”是两个状态：前者允许真实功能尚未实现，但规则和接口应明确；后者必须有真实执行结果。尚未实现的测试明确显示待接入或预期失败，不算通过。

## 一个直接关系样例的验收矩阵

这是直接关系这一类的测试设计，不代表全部权限情况，也不是本轮运行结果。更广的群组、角色、有效继承、OR/AND/排除、租户和上下文情况按 [权限清单](../../skills/business-observer/references/authorization-patterns.md) 选择。下面限定 R1 为一跳删除权限、D1 为 A→B、B→C；不能把它推广为所有层级规则都不继承。

| ID | 场景 | 独立预期 |
|---|---|---|
| R01 | 仅检查 A 是否可删除 B | 规则结果允许；不执行删除，不声称已经产生效果 |
| R02 | 仅检查 B 是否可删除 C | 规则结果允许 |
| R03 | 检查 A 是否可删除 C | 拒绝；A→B→C 的路径不继承一跳权限 |
| R04 | 合成数据将 C 的父节点由 B 改为 A | 新依据下 A→C 允许、B→C 拒绝；R1 本身不变 |
| R05 | 继续查看改父节点前的旧检查 | 保留当时结果和依据，显示对当前数据需要重新检查 |
| R06 | 读取 C 的关系失败或查询未完成 | 检查出错/证据不足；不画成已证明关系不存在 |
| R07 | 同时执行两个不同主体/对象的检查 | 输入、结果和解释分别绑定 check_id，不串用 |
| E01 | B 删除无孩子的 C，其他必要条件满足 | 按已明确的效果约定删除目标；核对真实存储与提交记录 |
| E02 | A 尝试删除 C | 无删除效果；不能仅检查页面显示“拒绝” |
| E03 | B→C 检查通过后、提交前，C 的父节点改为 A | 按本例提交前重查要求拒绝旧许可，C 保留 |
| E04 | A 删除仍有孩子 C 的 B | 孩子处理方式尚未决定时，该效果场景未决；不能用 R01 通过代替 |
| G01 | 把一跳规则错误实现为祖先可删除，再重生成图 | R03/E02 仍失败；不能靠让图迎合代码消除偏差 |
| G02 | 局部图折叠 B | 不产生 A 直接父于 C 的事实；边界可追溯 |
| G03 | 只改代码不改对应映射或模型 | 同步检查发现版本或结构失配 |
| G04 | 修改预期使错误实现通过，但没有相应需求变更 | 旧预期保护检查失败 |

E03 是用于检验提交前变化的建议场景；真实项目须在需求中明确其提交保护和一致性机制。树是否允许多父、环路、孤立节点，也由领域约束决定；确定为树后，再加入相应非法数据测试。

## 跨领域需要保留的检查

按本轮涉及的行为选择，不为无关功能运行全部组合：

- 状态：合法/非法事件、类型和范围、条件拒绝、失败/取消/重试与恢复。
- 并发：资源不足等待、资源足够时实际重叠、活动未全部完成不能汇合、旧新运行隔离、取消后实际结束才归还资源。
- 判定：替代授权、关系增删、参数/规则/时间变化、短路未求值、未知与拒绝分离。
- 效果：重复请求不造成额外效果，事务失败不产生“已提交”记录，检查通过后提交前变化得到处理。
- 观测：开启、关闭、抛错、队列满或丢事件时核对业务结果；缺失事实显示缺口。
- 局部图：执行 [F01–F10](focus-module.zh-CN.md) 的身份、边界、版本、交互与无副作用检查。
- 迭代：新增行为、修复 bug、纯重构分别比较图变化；旧证据不能作为新构建的通过依据。
- 交接与导出：换目录和新环境复现、相对路径、版本不兼容、冲突和未包含源码/数据的边界。

资源守恒、无权限不提交等是持续约束。等待何时一定恢复还依赖调度、公平性和外部服务假设；记录这些前提与测试期限，不能从几次运行推断所有情况下都会完成。

操作序列测试可借鉴 [Hypothesis 状态测试](https://hypothesis.readthedocs.io/en/latest/stateful.html)。定向改错优先在隔离副本里破坏关键规则，检查是否因预期的业务原因失败；仅检测到文件哈希变化不足以证明业务测试有效。

## 开发后的执行顺序

| 步骤 | 读取或执行 | 失败时如何处理 |
|---|---|---|
| 1. 输入核对 | 交接清单、需求、模型、源码/工具/测试内容版本 | 指出缺失或陈旧输入，保留旧记录 |
| 2. 静态与声明核对 | 类型、符号、调用候选、源映射、实际加载的机器定义、必需探针 | 输出受影响需求与节点；未解析不能算通过 |
| 3. 真实场景 | 开发前保存的初始数据、操作和预期，读取存储与返回值 | 定位预期与实际的差别，不改写预期 |
| 4. 过程核对 | 判定输入、活动状态、资源、等待/恢复、提交事件与效果 | 缺证据显示证据不足；结果正确也不能掩盖非法过程 |
| 5. 约束与检查反例 | 选择必要的序列测试、错误规则、漏映射和漏探针 | 若错误未被发现，补充检查并保留该反例 |
| 6. 人可理解的核对 | 用局部图解释一次成功、等待或失败，并定位关键源码和参数 | 图隐藏条件或无法定位时修正表达/映射 |
| 7. 接受与导出 | 同一候选的实际结果、覆盖、未知范围与复现材料 | 输入变化后旧验收失效；导出不等于重新验证 |

结果区分通过、失败、未运行、未实现、需求未决和证据不足。报告至少关联用例、需求、规则/模型版本、真实加载构建、数据依据、检查工具与实际命令结果。

原有 `change_sync begin/inspect/verify/accept/check`、状态机和内部活动检查可以复用并扩展。新模块接入前，不能仅因文档写有步骤就声称这些步骤已被程序强制执行。

对话中的核心验证内容是：展示之前约定的场景、当前实际结果、差异对应的局部图，以及需要澄清的行为选择。自动浏览器操作与独立 agent 试用分别留证，均不冒充真人理解效果测试。

## 编码 Skill 的交接契约

建议交接清单引用项目已有文件，不再另建一份重复的权威需求：

| 内容 | 交给编码 Skill | 编码后返回 |
|---|---|---|
| 目标与范围 | request、需求 ID、允许改变的规则、未决部分 | 实现的需求、未完成项与新发现的问题 |
| 图与规则 | 固定版本、稳定节点/边 ID、规则和状态声明、局部确认图 | 实际源码映射、生成图、映射依据及范围外说明 |
| 接口 | 数据类型、命令、效果接口、探针计划、模拟器范围 | 真实接口实现、探针位置和实际机器导出 |
| 验收 | 独立场景、数据与预期、必需检查、执行入口 | 实测结果与证据；不能只返回一句“已完成” |
| 环境 | 依赖锁、工具版本、项目约定、相对路径与启动方式 | 实际构建身份、运行环境、复现方法 |

编码阶段可选择项目合适的框架、分解和重构方式。影响已定行为时先返回具体差异；普通实现选择无需再次确认。新增必要的反例可以补充，改写原预期要关联真正的需求变化。

新对话只需交接说明、Skill、相关项目文件和合成材料即可继续。授权与需求来源保留必要摘要和定位，不要求转发完整聊天记录。

## Markdown、模型和代码的归属

- 自然语言说明保存业务意图与决定依据；执行声明保存精确的状态/规则语义。两者关联但不假定自动语义等价。
- 重复的结构化字段指定唯一编辑来源，其余由它生成。场景说明与验收输入尽量共用同一结构化场景。
- 业务状态机、权限与事务保护属于应用核心；可选观测接口、适配器、生成图和页面分别归属，剔除观察器不能剔除业务规则。
- 清单对每个产物记录路径、类别、来源、生成器和内容版本：源文件可编辑；生成文件编辑源后重建；运行证据保留历史。
- 现有项目的 `intent.json`、`discovery.json`、`acceptance.json`、`sync.json`、`behavior.json` 和源码位置可继续使用，由清单引用；不强制迁移目录，也不把同一需求在新旧格式各维护一份。

## 导出和共享的三种产物

| 产物 | 内容 | 可声明的能力 |
|---|---|---|
| Skill 安装包 | SKILL.md、脚本、模板、schema、版本、许可证与来源 | 安装方法和能力范围可复用；不包含某个项目的真实业务数据 |
| 项目复现包 | 相关规格/决定摘要、规则与映射、测试和合成数据、运行适配、依赖锁、明确选入的源码或精确源码引用、工具版本及清单 | 材料齐全并在新环境实际重跑后，才能声称可复现 |
| 图审阅包 | 指定版本的完整/局部图、必要边界和来源、选中的别名备注、Markdown/SVG/HTML 等静态输出 | 可理解和讨论该快照；不冒充当前运行，也不承诺包含源码或可重新执行 |

运行数据库、私密参数、凭据、原始聊天和本地绝对路径不默认导出。需要实际运行材料时明确选取、限定字段并标记处理后的范围；合成数据用于公开示例。导出中排除内容不把事实改成“没有”。

清单包含文件校验值、schema/Skill/生成器版本、规则与模型版本、源码提交及未提交内容摘要、场景和预期版本。实际数据的版本另记，不将 Git 提交当作数据库快照。

导入先检查格式、路径、版本和依赖，不自动执行包内脚本。缺少源码或无法获取依赖时明确只能审阅。归档中的脚本只有在可信项目环境、明确执行范围内运行；路径不能越出目标目录。

`install_skill.py` 用于安装，`architecture_guard.py` 用于核心包导出；v0.4 的 `project_bundle.py` 按显式清单生成项目或图审阅包，检查路径、文件大小和内容哈希，不自动执行导入内容。多用户语义冲突仍由项目版本控制和人工确认处理。

## 同步开发与冲突处理

1. **稳定身份。** 项目、需求、规则、定义节点和边使用稳定 ID；显示改名不改身份。源码符号移动后更新映射；确需换 ID 时提供迁移表，不复用旧 ID 表示另一含义。
2. **版本基线。** 每项语义修改携带 base_revision 和受影响需求。对过期版本的修改检查冲突，不直接覆盖。
3. **分开合并。** 规格/代码/测试走项目已有版本控制；个人位置和标注保持独立，可选择导出。共享名称或规则发生冲突时显示双方差异，不按最后写入静默决定。
4. **生成物重建。** 合并源文件后重生成图，避免手工合并陈旧生成片段；图与运行事实始终绑定版本。
5. **验收作废。** 需求、规则、代码、映射、验证脚本、依赖或工具变化后，核对受影响检查。旧报告可以查看，但不能成为新版本验收。
6. **加载版本。** 开发中的候选模型与运行中的旧程序分别显示。磁盘代码更新后，只有实际重新加载并核对构建身份，才关联新运行事实。
7. **可恢复交接。** 保存开发前、待编码、待验证、失败、已验收状态及材料清单。恢复时先核对内容版本；不从聊天最后一句“完成”恢复通过状态。

本阶段使用 Git 和显式导出即可，不要求先建设云端实时协同服务。校验值用于发现漂移，不构成抵抗任意篡改的签名证明。

## 后续独立试用的任务

给另一编码流程本 Skill、一个真实开发需求和最少原始材料，不提供预期实现或已知缺陷答案。观察它是否能：

1. 提炼业务网，针对影响行为的歧义提出具体问题，正确吸收部分答案与修订。
2. 生成能核对的执行声明和独立预期，完成编码交接。
3. 实现后使用原场景验证，发现规则范围/组合错误、参数偏差、漏探针或过期图。
4. 用局部图解释失败、修复并保留需求依据。
5. 在另一目录复现导出包，恢复图身份和所选标注。

试用结果以实际执行记录为准，不能用本设计清单代替。模拟用户与独立开发会话的过程须注明身份；最后通过材料绑定最终 Skill 和项目版本。
