Choose at the beginning

Observe the application.
Or also drive its state.

Both modes keep the graph, source mappings, and runtime monitoring. The distinction is which mechanism executes the business transition.

DRIVE

Develop from the state declaration

State declaration→Native executor→Business effects

A project-local engine consumes the declaration. Guards, transitions, and actions are explicit and checked. Unsupported semantics fail instead of silently disappearing.

OBSERVE

Keep the project's own logic

Your functions→Actual state + effects→Graph evidence

The application makes its own decisions. Adapters capture real transitions, inputs, and outcomes. The observer does not run a second, competing business state machine.

{ JSON }

Python maintains the shared graph, validation, recording, export, and viewer. Python or JavaScript adapters keep execution native. Observation failure must not stop the business operation.

The native Python/JS bo.fsm/1 executors support a validated flat state-machine subset. The complete Python examples also cover activities, resources, waiting, joins, and recovery. More complex native engines require an explicit adapter.

From the first conversation to the next iteration

Make the behavior visible
before, during, and after coding.

You describe the change and inspect the result. The coding agent maintains the declarations, source bindings, probes, and checks alongside its normal development work.

  1. 01

    Confirm the intended flow

    See a small graph in the conversation, with a live Web link. Correct it in conversation. Clarifications and counterexamples resolve ambiguity in what you meant; they do not add recommended features.

    Your intent → a confirmed graph
  2. 02

    Build with the graph attached

    The agent uses your chosen coding approach. It binds important functions and parameters, adds identifiable probes, and scans source changes independently of the existing graph.

    Code changes → updated mappings
  3. 03

    Check, repair, and inspect

    Run the confirmed scenarios and independent checks. Missing mappings, invalid states, or wrong values block acceptance. Repair code and graph, rerun the checks, then inspect the updated network.

    Evidence → an accepted iteration

A graph can faithfully expose a business bug. A mapping pass does not turn that bug into a business pass. Expectations come from confirmed intent and independent reads, not from the graph checking itself.

Synchronization runs within each agent-managed coding batch. A Skill is not a background daemon for every editor; scan/watch reports drift, and the active coding agent must reconcile it before accepting a change.

See a real operation unfold

Record it. Inspect each change.

Choose all instrumented events or a focused region, start recording, operate the application, and stop. Replay exposes changes to state and values alongside their actual source.

Choose scope→Start recording→Use the application→Stop and replay

Illustrative replay, not a live trace. In your project, only captured facts are shown. Missing events, dropped records, and unknown values stay visible as gaps.

Focus without losing meaning

Record a selected region when that is enough. Or record all instrumented events and change the view afterwards. A business view groups meaningful changes; a function view reveals captured calls and values.

Show what actually moved

Replay shows before/after values. Flow on an edge needs actual call or dependency evidence; nearby timestamps and a static edge do not prove that information passed between nodes.

Keep your working view

Expand regions, drag groups, pin nodes, add names and notes, and save custom views. The project keeps your layout. These view operations do not create business events or execute business commands.
