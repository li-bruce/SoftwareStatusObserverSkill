# 是否需要很多 `/xxx` 命令

结论：需要清楚的能力边界，不需要让用户记住很多命令。日常保留一个 `business-observer` Skill 入口，后台维护随每轮开发执行。

## 现状

仓库已经提供建图、聚焦、扫描、检查、升级、打包等 Python CLI；这些不是自动注册的聊天斜杠命令。`agents/openai.yaml` 只定义 Skill 的显示信息和默认提示。

Codex 的官方示例支持通过 `/skills` 选择技能或用 `$` 引用技能；这不能据此理解成每个 Python 子命令都会变成 `/bo.xxx`。[官方说明](https://developers.openai.com/blog/eval-skills)

## 用户需要的入口

| 用户表达 | 处理方式 | 是否需要独立斜杠命令 |
|---|---|---|
| 使用 `$business-observer` 开发或修改这个功能 | 识别新建/已有项目，必要澄清，维护图、探针和检查 | 一个 Skill 入口足够 |
| 打开图，只看这一段 | 启动或复用 Web，聚焦局部图 | 自然语言或页面按钮即可 |
| 检查图是否完整对应代码 | 运行阶段验收，分别报告映射、状态约束和业务检查 | 可作为将来的少量快捷入口之一 |
| 导出图或分享项目 | 按现有导出功能处理，并说明包含的数据 | 自然语言足够；高频时再加快捷入口 |
| 隐藏/关闭调试页面，保留程序运行 | 用已有 Web 模式或核心包导出，不删除状态模块 | 自然语言足够，说明具体影响 |

同步、探针接入、静态扫描、生成、校验、审阅变更、接受基线应由 AI 根据开发过程调用。要求用户逐个调用，会破坏“开发过程中无感维护”的目标。`accept` 尤其不能成为跳过验证的快捷操作。

## 何时再增加快捷命令

仅在真实使用证明某项操作频繁且目标明确时增加。命令应分派到同一套实现和检查，不维护第二套提示逻辑，也不因命令调用跳过确认或校验。不同宿主对斜杠命令的支持不同；当前不宣称已经提供自定义 `/bo.*`。

本次只做能力与入口分析，不新增一批命令或改变安装方式。
