# 过程观察

## 对话阶段

- 初轮实际提出 3 组问题：派生内容、权限来源、类型/端口和传输效果。没有推荐答案。
- 用户说明独立创建的项目也能连接后，助手接受了修正，不再把派生作为连接的必经步骤。
- 手动执行带来一处尚未说明的写入权限，助手新增 D4，而没有重新问已回答的 D1–D3。
- 协调者有意使用一句不完全明确的回答：“执行也要有两边的 connect 权限。不过连接配置的时候已经授权过了，后面就按这条连接执行就行。”原意仍以测试开始前的 intent-fixture.md 为准，没有改变预期。
- 助手自行提出配置后撤销目标端权限的反例，只确认授权时点。D4 保持 open，原有决定保持 resolved。
- 用户澄清按当前权限重新检查后，助手进入实现，没有继续主动引入审批、队列、重试或内容业务校验。
- 这些观察来自本次实际单条对话，不代表任意模型或输入都能做到。

## 环境与测试脚本

- 第一次需求轮耗时约 595 秒，其中包含设计图生成和本机页面启动排障。首轮问题已经明确时，页面排障延迟了向用户提交问题。这是使用流程可改进之处。
- 开发会话曾报告服务启动，但 HTTP/浏览器无法连接，并如实记录未验证。协调者以隐藏窗口在宿主环境启动原版服务，8866 的 /api/view 返回 200。开发会话随后独立复核了 HTTP 和页面。此项有协调者环境协助，不能声称完全无干预。
- 协调者的 Python Playwright 辅助依赖首次安装遇到沙箱临时目录权限问题，改用项目内临时目录后成功。只安装在 .validation/browser-python，未加入被测应用依赖。
- 协调者页面脚本的第一次等待 networkidle 超时；图会持续轮询，后续改为先尝试网络空闲，再检查实际渲染完成。
- 第二次就绪判断误读 graphDebug.graph.nodes，实际接口为 graphDebug.graph.boxes。该错误属于审查脚本，不是 Skill 图运行故障。诊断输出和复测截图分别保留在 browser/03-design-diagnostics、browser/04-design-verified。复测无页面异常，WebGL 渲染成功。
- 控制台仍有一条资源 404，尚未据此判定业务或渲染失败；后续运行页检查会记录具体请求。

## 实现阶段发现的问题

- 开发会话自己发现：一个场景的创建类型与冻结预期不一致，修正场景输入；SQLite 连接没有及时关闭，导致 Windows 清理测试数据库失败，修正连接生命周期。原日志保留在项目 evidence/failures/implementation-01。
- 浏览器实测发现：查询适配遗漏页面需要的字段，且探针尝试 ID 与操作实例 ID 不一致。修复接入后再做页面与完整门禁，不把此前脚本通过等同于页面可用。
- 白盒约束在实现后补写，未遵守 Skill 中实现前保存关键参数预期的要求。不能回写历史把它包装成遵守流程。初始业务 cases 在编码前已有记录，协调者的用户意图也在启动前固定，但这些不能代替缺失的前置白盒约束。
- 初次录制只有事件与 JSON 变化，缺少逐事件完整状态帧。协调者用 check_record_frames.py 独立复现：26 个事件、0 个状态帧。执行身份能对应实例，与能还原每一步状态是两项不同检查。
- 修复前源码已封存为 snapshots/01-before-runtime-frame-fix.zip，并有文件哈希。协调者要求先冻结补测预期，再修复接入、补回归和复测；这次修复有审查反馈，不能算作初次无干预成功。
- 个人视图复核：设计阶段实际拖动并保存的坐标、名称、批注和核心标记，在运行图中保留；同一节点仍能展开。证据见 browser/06-design-personal-view-retest 与 browser/07-runtime-personal-view。

## 修复与复测结果

- 新会话先冻结状态帧预期并在旧实现中运行失败，再补齐实际事务中的采集；原失败和测试原件保留，未改原业务预期。项目回归最终为 17 项通过。
- 协调者重新读取实际 HTTP 导出与记录，独立核对 26 个事件/26 个状态帧、运行/构建/操作身份及检查中/已提交/已拒绝状态。公开导出和保存记录中的帧一致；最终状态没有被拿来替代早先步骤。结果在 execution/frame-binding-repaired.json 与 execution/03-initial-delivery-audit/。
- 当前实现独立重跑 18 项业务/严格状态检查通过。以直接 SQLite 读取核对结果，不读取项目用例的预期值。检查时源码哈希保持不变，见 execution/02-initial-repaired/report.json。
- 个人视图在状态帧修复后再次通过真实浏览器检查；坐标、名称、批注和核心标记未丢失。点击同一节点仍可展开，见 browser/11-repaired-personal-view/。
- 初始助手把业务描述成顺序主线，模拟用户说明“派生不是连接的前提”后，最终图有 independent_project_connection 边，程序也允许独立项目连接。必须把这处修正保留在对话评价中，不能说最初理解就完全正确。
- 本次修复的是试用项目的适配和接入。共享 Skill 代码未修改，不能据此声称其他 AI 开发的项目会自动避免相同遗漏。

## 额外迭代的授权边界

首版完成后，协调者尝试发送预先拟定的合成迭代“派生时可指定另一种已有类型”。自动审批拒绝该消息，认为用户没有明确授权这条具体业务变更及证据管理消息。该消息没有发送成功，没有执行对应业务变更；协调者已向用户请求确认。此项不记作失败的业务实现，也不记作已完成的迭代验收。

首版及监控修复已经完成的证据不受影响；修复前、修复后源码和项目原始证据分别封存于 snapshots/。首版封存时按“派生默认且只能同类型”的已确认规则运行。

## 获得授权后继续迭代

用户随后明确回复“允许继续测试这条迭代”，协调者已将相同业务变更与保留记录要求发送至原会话。开发助手未再次追问已明确的规则，开始冻结新增预期并检查旧实现。

独立检查 check_iteration.py 先运行于封存源码的解压副本，25 项中 9 项原有默认派生检查通过、16 项需要新类型参数的检查失败；失败来自旧接口不支持该参数。第一份审查脚本暂用 project_type 为新增参数名，开发会话实际定义为 target_type，因此仅调整三个调用的参数名；原脚本保留于 execution/04-iteration-on-frozen-old-code/check_iteration.initial.py。随后在同一旧源码副本重跑，后续复测沿用调整接线后的同一脚本和未改变的业务断言。

开发会话的前置测试实际发现 HTTP 旧接口会忽略目标类型，产生错误类型的项目。功能修改后检查通过；同步 inspect 又以 decision_changed_without_history 拦住缺失旧 D1 副本的变更记录。助手从本轮归档补齐旧决定后复测，没有改写旧答案。

协调者在新实现重跑 25 项新增检查和 18 项原有检查，全部通过，检查期间源码哈希未变。11 项前后比较确认原断言与图身份未删除、未弱化。新录制 26 个事件/26 帧独立核对通过，公开导出与当前模型和保存帧一致。

个人视图首次复查的脚本存在状态假设错误：节点原本已展开，脚本点击了“收起”后仍等待展开。坐标、批注和核心标记当时已通过；没有页面异常。保留 browser/13-iteration-personal-view 的失败、截图和原脚本，改为先检查真实按钮状态再执行展开，browser/14-iteration-personal-view-retest 通过，未改应用代码。
